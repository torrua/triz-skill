> **Главная аксиома:** Сначала ищи изобретательское решение, улучшающее параметр $A$ без ухудшения параметра $B$. Если этому препятствует непреодолимый физический, математический, юридический, бюджетный или контрактный предел — открыто зафиксируй предел и его доказательства, вместо того чтобы выдумывать ложные гарантии.

## Что это такое?

Навык для ИИ-агентов, применяющий **ТРИЗ (Теорию Решения Изобретательских Задач)** Генриха Сауловича Альтшуллера и современные инструменты ТРИЗ (Злотин/Зусман, Литвин/Герасимов, ОТСМ-ТРИЗ Хоменко). Навык проводит агента по 5-шаговому конвейеру **АРИЗ-AI (ARIZ-AI)** для устранения противоречий за счёт внутренних ресурсов системы (ВПР), классифицирует ограничения (`Hard`, `Soft`, `Assumptions`) и строго отделяет проверенные факты от гипотез.

## Установка

### 1. Кроссплатформенный установщик (Рекомендуется — Python 3.10+)

Устанавливает навык и проверяет побайтовое совпадение по SHA-256:

```bash
# Google Antigravity (~/.gemini/config/skills/triz-universal)
python scripts/sync_deployment.py --mode apply --platform antigravity

# Claude Code (~/.claude/skills/triz-universal)
python scripts/sync_deployment.py --mode apply --platform claude-code

# Cursor (~/.cursor/skills/triz-universal)
python scripts/sync_deployment.py --mode apply --platform cursor

# OpenAI Codex CLI (~/.codex/skills/triz-universal)
python scripts/sync_deployment.py --mode apply --platform codex

# Произвольный или проектный путь (например, .claude/skills/triz-universal)
python scripts/sync_deployment.py --mode apply --destination "/path/to/.claude/skills/triz-universal"
```

### 2. Claude.ai (Веб-версия и настольное приложение)

Соберите чистый архив `dist/triz-universal-v3.0.0.zip` для загрузки в **Claude.ai → Settings → Capabilities / Skills**:

```bash
python scripts/sync_deployment.py --package-zip
```

### 3. Ручное копирование / PowerShell

```bash
# Linux / macOS (Antigravity или Claude Code)
cp -r triz-universal/ ~/.gemini/config/skills/triz-universal/
cp -r triz-universal/ ~/.claude/skills/triz-universal/

# Windows (PowerShell)
.\scripts\sync-deployment.ps1 -Mode Apply -Destination "$env:USERPROFILE\.gemini\config\skills\triz-universal"
```

## Сквозной пример: До и После (Layer 1 и Layer 2)

**Запрос:**
> *«Торговое ядро на C++ имеет жёсткий бюджет `<5 мкс` на обработку ордера. Регулятор требует логировать каждый переход состояния, но запись на NVMe-диск занимает `45 мкс`. Как спроектировать систему?»*

### ❌ Без навыка (Типичный компромисс базовой модели)
> *«Поскольку запись на диск занимает 45 мкс при бюджете 5 мкс, компромисс неизбежен. Разумным балансом будет логировать только 1% транзакций через сэмплирование или буферизовать логи в обычной куче со сбросом раз в 5 секунд, приняв небольшой регуляторный риск».*

### ✅ С навыком `triz-universal` — Уровень 1 (Layer 1, ответ по умолчанию простыми словами)
> **Решение (Разделение фиксации в памяти и физического сброса на диск):**
> Вместо форматирования и записи на диск внутри торгового потока, записывайте фиксированную 64-байтную бинарную структуру в заранее выделенный неблокирующий кольцевой буфер разделяемой памяти (`mmap` / `io_uring`) одним атомарным сдвигом указателя (`~10–30 нс`). Выделите отдельное ядро CPU под фоновый поток, который непрерывно сбрасывает страницы кольцевого буфера на NVMe-диск вне критического пути ордера.
>
> **Допущения, остаточные пределы и как проверить:**
> - *Допущения и пределы:* Предполагается наличие свободного изолированного ядра CPU. При мгновенном обесточивании сервера до сброса буфера хвост записей за последние миллисекунды может быть потерян, если не используется NVRAM/ИБП.
> - *Как проверить:* Замерить p99.9 задержку горячего пути на пиковом бурсте (`<5 мкс`) и убедиться, что размер буфера исключает переполнение при паузах сборщика мусора NVMe.
>
> *«Хотите, я подробно покажу, как именно ТРИЗ-алгоритм привёл нас к этому решению (с разбором противоречия, скрытых ресурсов и применённых приёмов)?»*

### ✅ С навыком `triz-universal` — Уровень 2 (Layer 2, Профессиональный ТРИЗ-паспорт по запросу)
```markdown
### 💡 ТРИЗ-Изобретательское Решение
- **Классификация ограничений:** Жёсткие: [бюджет <5 мкс на горячем пути, 100% логирование переходов состояния] | Мягкие: [мгновенность сброса на диск] | Допущения: [наличие свободного изолированного ядра CPU]
- **Тип исхода:** Противоречие устранено
- **Физическое противоречие (ФП):** Ввод-вывод телеметрии должен выполняться синхронно при каждом переходе состояния (для 100% регуляторной полноты) И НЕ должен выполняться в потоке ордера (чтобы уложиться в бюджет <5 мкс).
- **Диагностический путь:** КОГДА / СТРУКТУРА
- **Примененная стратегия:** Во времени и По структуре
- **Использованный прием(ы):** Прием №10: Предварительное действие (предаллокация буфера), Прием №24: «Посредник» (кольцевой буфер разделяемой памяти между горячим потоком и NVMe)
- **Мобилизованный ресурс (ВПР):** Свободное изолированное ядро CPU, страничное отображение памяти ОС (`mmap` / `io_uring`), выравнивание по 64-байтной кэш-линии CPU
- **Решение:** Горячий поток пишет 64-байтную структуру в lock-free кольцевой буфер за ~20 нс; выделенное фоновое ядро асинхронно сбрасывает страницы на NVMe.
- **Доказательная база и уверенность:** Паттерн (`C-IOURING-01` в CLAIMS.md) — проверенный архитектурный паттерн; точный p99.9 зависит от железа и настроек ядра Linux.
- **План верификации:** Базовая линия: 45 мкс синхронной записи. Эксперимент: воспроизведение пикового потока 1 млн ордеров/с на изолированных ядрах. Порог успеха: накладные расходы горячего пути p99.9 < 100 нс, 0 потерянных фреймов. Предлагаемая роль для проверки: инженер по производительности систем.
- **Остаточные риски:** Риск потери хвоста буфера в ОЗУ при жёстком отключении питания (устраняется через энергонезависимую NVRAM или синхронную репликацию в память второго узла).
- **Ожидаемый результат и статус проверки:** Статус: НЕ ПРОВЕРЕНО (ожидаемый эффект при указанных допущениях: задержка горячего пути <100 нс при 100% полноте аудита).
```

## Когда навык НЕ нужен и ограничения (Limitations)

`triz-universal` — специализированный инструмент разрешения системных противоречий, а **не** замена обычной отладке.

### Когда навык НЕ нужен (`When NOT to Use`)
- **Обычные баги и ошибки очерёдности блокировок (DB Deadlocks):** Если PostgreSQL выдаёт `deadlock detected` из-за того, что транзакция А блокирует строку 1 затем 2, а транзакция Б — строку 2 затем 1, нужно просто отсортировать порядок блокировок (`ORDER BY id`), а не изобретать новую архитектуру.
- **Оптимизация одной метрики без конфликта:** Добавление пропущенного SQL-индекса или замена $O(N^2)$ цикла не ухудшает встречный параметр.
- **Простые прототипы и явный запрос на компромисс:** Если разработчик пет-проекта явно просит выбрать TTL кэша (10с или 60с), навязывание сложной архитектуры избыточно.
- **Мета-вопросы о ТРИЗ:** Вопросы *«Что такое ТРИЗ?»* или проверка орфографии в файлах не запускают ТРИЗ-паспорт.

### Известные ограничения
1. **Расход токенов и времени рассуждения:** Диспетчер `SKILL.md` занимает ~6.5k токенов контекста, а выполнение конвейера АРИЗ-AI требует ~400–900 токенов внутреннего рассуждения.
2. **Не заменяет инженерную и юридическую валидацию:** Языковая модель не может провести реальный бенчмарк или выдать юридическое заключение по GDPR/KYC. Все результаты по умолчанию помечаются как `Статус: НЕ ПРОВЕРЕНО`.
3. **Стохастичность базовых моделей:** Скрипт `evals/run_evals.py` детерминированно проверяет правила маршрутизации и эталонные ответы (а также поддерживает `--responses-file` для проверки живых API-прогонов), однако при переходе на новые версии моделей требуется проведение слепой экспертной оценки по протоколу [evals/README.md](evals/README.md).
